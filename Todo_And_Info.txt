The game flow is being reworked to follow a more simple approch:
	-Game Hander will act as an extention to the main game logic. It 
	role is setting up listerns to other handlers and regulating the program flow.
	Note: it should be treated as hidden to other system
	
	*Below are self contain (global) handlers. They should worry only about their children
	but other nodes can acess them. The child nodes of the handler do not nessary need to
	follow this rule.
	
	-UI Handler: regulate and host the persistent UI node. It meant to be a shared
	UI for all systems instead of having to relaod the UI all the times and reloading
	its state.
	
	-Player Handler: the owning player controller in other words. Handles input config
	replated to pawn control and may ref controlled units. Also may extend logic to the active
	camera.
	
	-World Handler: The middle man that help with world transition as well as other
	logic realted to the world state that indivitual level do not need to worry about
	(unless they need to modify or listen to it).
	Note: this should not hold  the active level. this help with the presistant state
	of the world.
	
	-Data Handler: this handles savinga and loading as well as other file system
	logic dealing with acessing or handling data. Most of the game states will be 
	stored here unless a system want to handle it directly, then it can request it
	from the data handler so it do not need to know the directory format.
	
	*Other handler may be added/used, but above are the current the main ones.
	
	-The level will be the game main scene. so it will use the root current scene.
	this allow the game to work better with godot and allow levels to do what ever they want.
	in other words any node can be a level, but active system may not work or act incorrectly
	if not handle correcly before the switch (example is ui elemets unrealted to the level
	may render if not hidden or unloaded on level switch)
	Note: level can be 2d, 3d, control, or a mix of these, but there should only be one
	active level. A handler can be made to handler paralle levels if needed, but the level should
	try to handle that itself without exposing it globally.
	
	-acess to nodes outside it scope should be done via groups, traces, signals, or by handler.
	acessing the root or scene tree (out side of the game handler) to get a node ref should be avoided
	getting the current scene may be an exception, but may be better to have the world
	directly store it and the game set and unset it. Also may be best if the level
	is not know to other systems that do not handle it. Ideally the world, data, or another handler
	should hold the data publicly avaible to the game.
