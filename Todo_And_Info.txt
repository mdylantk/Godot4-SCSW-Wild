	of the dir.

The game flow is being reworked to follow a more simple approch:
	-Game or Game handler will handle most of the persistant states. 
	Its children or other subsystem/plugins will handle others
	-cross comunication will be done with the persistant states or other
	resources that share a loaded path. This only applies to things that Godot
	do not provide by its included nodes or servers (onless that approch is slower).
	-The game scene should always be active to regulate the game so it will be an
	autoload or attach to the root at the app start.
	-events are handled by the states instead of a dedicated event object since
	most events tend to affect the state and would require more hookups to split 
	them.
	-Action system will be kept to add logic block via the editor. It will be simplified
	to expect only the source and its targets and additonal data to be assumed by
	those nodes groups and metadata as well as conditions of exicutions (for example:
	interactions are limited to player character when expecting a player character.
	should try to use groups to verify source or target is a player or the active
	player)
	-Beside the custom system, most things should try to work with the way godot
	editor is set up to be used. main level or active scene being the current 
	scene using godot ways of loading and unloading it. The use of groups for 
	grouping up nodes. 
	
Note on the save system:
	Originally I was going to save and load the state, but managing the
	conections and ref after attemping to take over the path made it more trouble
	that I would like. Instead loading and saving expects a dictionary to convert
	to a string either by adding it to a config file, a resource with an exported
	dictionary, or directly into a string (like json). Also, if possible, could 
	make it into some binary format or somthing as long as a dictionary can be
	converted too and from it.
	NOTE: this also allow save data to be compress into a single file if desired.
	The plain is to do that with most of the persitant states and only save
	character and level state in their own files (or compressed in a diffrent one.)
	
Note on items:
	-There will be two types of storage for basic and advance items. Basic is
	a standard table of the item_type uid and the amount where advance will be
	a slot base inventory(an array of dictionaries). For saving reasons, the 
	advance items will be stored (long term) as a dictionary instead of the item
	object. The item object is reserver for modifing an item in editor and for
	system to load it as such for type safe use. This is to try to make it support
	non-resource base save formats where one may not want the item script to be an
	editable field. (Note: uid is stored and may be a problem, but I think that 
	requires modding the game to add uid to external resources so converting to a
	non-resource saving system should prevent such issue as long as modding and hacking
	is not a consern)
	-NOTE: item types (like for extended item types) may end up using a base
	class and use a text file to populate it in the future depending how large 
	the item database get for similar items (for the fish for example). This would
	set the item metadata to what in these text files to override the item info.
	It will allow remove items not to be an issue, but also means that remove items
	would also be kept. This could be a problem for scores and status that depends
	on certain info (such as name), but could be solved by reserving this meta for
	special item and use the item type name instead (example: Walleye is an item_type.tres
	and King Walleye is a variantion of Walleye. the player fish log will treat it
	as a Walleye. This would mean rare fish would be a subgroup of the fish type in
	the log and metadata would be used to state where the subgroup if walleye is
	rare or not)
